# 2026-11-04 — Fix "Failed to fetch" on client login

## Root cause
- Client login (`handleLogin`, role === 'client') was hard-wired to **Supabase Auth**
  (`client.auth.signInWithPassword`) with **no fallback**; it `return`ed inside the catch.
- The project's Supabase host `evdwvklmrgyovzthaffv.supabase.co` is **unreachable**
  (verified: supabase.com loads fine, but the project host returns `fetch failed` —
  almost certainly paused/deleted). So every client login threw a bare
  `TypeError: Failed to fetch`, surfaced raw in the toast.
- The demo credentials advertised in the auth modal (`client@kgc.ph / password`)
  live in the **local** server store (`DEMO_USERS` in server.js), not necessarily in
  Supabase Auth — so they could never work while Supabase was the only path.

## Changes

### index.html
- Added local-account fallback helpers after `getSupabaseClient()`:
  `isNetworkAuthError`, `isLocalClientSession`, `loginAgainstLocalStore`,
  `registerAgainstLocalStore`, `setLocalClientUser`, `finishClientLogin`,
  `describeClientAuthError`.
- `handleLogin` (client branch): try Supabase → on any failure fall back to
  `POST /api/auth/login` (role client) → `setLocalClientUser()` + `finishClientLogin()`.
  Only if both fail show a human-readable toast (network vs credential specific).
- `setLocalClientUser` stores a **synthetic** user object with `__local: true` in
  `portalState.supabaseAuthUser` so `isSupabaseClient` / dashboard / header menu keep working.
- `handleRegister` (client branch): on network failure falls back to
  `POST /api/auth/register`, then signs in locally.
- `logout`: skips Supabase `signOut()` for local sessions, and no longer hard-blocks
  when Supabase is unreachable (previously trapped the user signed in forever).

### server.js
- `persistBooking`, `persistBookingUpdate`, `persistUser`, `persistUserUpdate` now
  **try Supabase first and fall back to the JSON store** on error. Previously reads had
  a JSON fallback but writes returned the Supabase call directly → 500 while Supabase
  was down (broke booking submission and registration).

## Notes / gotchas
- Local client sessions are **not persisted** across refresh — `loadState()` deliberately
  refuses to restore client sessions from localStorage (Supabase session is the source
  of truth). Acceptable; user re-logs in.
- `findUserByCredentials` always checks `DEMO_USERS` after the registered store, so
  `client@kgc.ph / password` works via the API even when `data/users.json` is non-empty.
- Writes now may split data between Supabase and local JSON while Supabase is down.
  Reconcile when the Supabase project is restored.
- **This session the Bash tool was broken** (`PortableGit/usr/bin/bash.exe` not found),
  so no `node --check` / browser verification was possible. Changes reviewed statically.

# 2026-11-04 — Registration false "email already exists"

## Confirmed defects
1. **Double insert** — `/api/auth/register` did `persistUser(newUser)` *and* then
   `usersStore.push(savedUser)`. `persistUser` already pushed in the JSON path, so every
   registration was written twice. Proof: `data/users.json` had two identical rows with
   id `USR1793768148841`.
2. **Case-sensitive DB lookup in `upsertClient`** (`supabase-store.js`) used
   `.eq('email', ...)`. Postgres `=` is case-sensitive, so `User@x.com` missed an existing
   `user@x.com` row → insert → and because the column UNIQUE is also case-sensitive, a
   *second* row for the same address could be created. The app's case-insensitive
   duplicate check then matched it → false "already exists".
3. **Blank-email rows could match** — comparison against `''` when input was whitespace.
4. **Unique violation swallowed** — `persistUser` caught every Supabase error and fell
   through to the JSON store, so a real duplicate silently created a second account; and
   unrelated insert failures were also downgraded to a JSON write.
5. **No transaction / race handling** — check-then-insert with no reliance on the DB
   constraint; endpoint had no try/catch, so a `23505` became a raw 500.
6. **`USR${Date.now()}`** ids could collide under concurrency.
7. **`upsertClient` UPDATE rewrote the primary key** (`payload.id`), risking the
   `bookings.user_id` FK.

## Fixes
- `server.js`: added `normalizeEmail`, `isBlockingAccount` (skips blank emails and
  `Rejected`/`Deleted`/`Archived` rows), `findAccountByEmail`, `dedupeUsers`,
  `isUniqueViolation`, `upsertUserInMemory`.
- `loadUsersFromDisk` now dedupes and rewrites the file once.
- `persistUser` upserts in memory and **rethrows** unique violations instead of masking them.
- `/api/auth/register` rewritten: normalize once, validate format, dedupe snapshot,
  log which row matched on 409, no double push, random id suffix, try/catch mapping
  `23505` → 409 and everything else → 500.
- `supabase-store.js`: `upsertClient` lowercases the email, uses `ilike(...).limit(1)`,
  and no longer sends `id` on UPDATE.
- `supabase-schema.sql`: dedupe by `lower(email)` then
  `create unique index users_email_lower_uidx on public.users (lower(email))`.
- `index.html`: maps Supabase's "already registered" to the app's standard message.

## Still unverified
Shell still broken → no `node --check`, no runtime test. The new
`⛔ Duplicate email blocked: <email> matched id=… role=… status=…` log is the way to
identify the offending row if it recurs.

# 2026-11-04 — Email campaign features (welcome + booking confirmation)

**Already existed** before this task: `mailer.js` (nodemailer transporter, `sendWelcomeEmail`,
`sendBookingConfirmation`), `queueEmail()` in server.js, and both call sites
(`/api/auth/register` line ~783, `/api/bookings` line ~546). `nodemailer` is installed in
`node_modules`. So the work was an audit + hardening, not a from-scratch build.

## Defects found & fixed
1. **Booking double-write** — `/api/bookings` did `persistBooking()` *and*
   `bookingsStore.push(savedBooking)`; same bug class as users. Added
   `upsertBookingInMemory()` and removed the extra push.
2. **Duplicate welcome emails** — `/api/users/sync` sent a welcome on *every* call, but it
   doubles as a profile sync (called on each client login). `upsertClient()` now returns
   `{ user, created }` and welcome only fires when `created === true`. Same for the JSON path.
3. **Schedule fields dropped** — the client sends `timeSlot` / `meetingFormat` / `duration`
   but the endpoint's whitelist discarded them, so the email could never show them. Added to
   the booking object and merged back for the email via
   `Object.assign({}, booking, savedBooking)` (Supabase `mapBooking` doesn't return them).
4. **Mailer had no retry / no config diagnostics** — rewrote `mailer.js`.

## mailer.js (rewritten)
- Lazy `readConfig()`; never throws at require time (a missing SMTP config must not crash boot).
- `isConfigured()`, `verifyConnection()` (probed once at startup, non-fatal).
- `pool: true` transport; retry once with backoff, **not** on `EAUTH`/534/535 or
  `EMAIL_NOT_CONFIGURED`.
- Shared `renderLayout()` — table-based, inline styles only (clients strip `<style>`),
  dark header + gold brand accent.
- `formatBookingDate()` → "October 14, 2026" (parses leading Y-M-D to avoid TZ day shift).
- Booking email rows: reference, status pill, per-subsidiary services, payment method,
  formatted date, plus optional time slot / meeting format / notes.
- Exports: `isConfigured, verifyConnection, sendMail, sendWelcomeEmail,
  sendBookingConfirmation, formatBookingDate`.

## Other
- `.env.example`: documented `SMTP_REPLY_TO`.
- Startup banner prints whether email is configured and the SMTP verify result.
- `queueEmail()` unchanged — `setImmediate` + `Promise.resolve().then(send).catch()`, so a
  sync throw or network failure is logged and never touches the HTTP response.

**Not verified**: shell still broken, so no `node --check` and no live send test.
